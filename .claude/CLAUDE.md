# 共通指示

- 回答、説明、作業報告、PR の説明文、コミットメッセージは日本語で書きます。
- コードは既存のスタイルに合わせ、不要なコメントは追加しません。コードコメントの言語も既存のコードに合わせます。
- 調査タスクでは、必ず情報源を示します。
  - Web で調査した場合は、参照した URL を示します。
  - 実装を調査した場合は、参照したファイルのパス（可能なら行番号も）を示します。
- コマンドを実行するときは、実行前にそのコマンドが何をするものかを説明します。
- 編集するときは、簡単に解説をします。
- `git push` は、ユーザーから明示的な指示があるまで実行しません。Auto-mode でも同様です。
- `gh` コマンドで pull request を作成するときは、`--draft` を付けて作成します。ブランチが未 push の場合は、PR を作成する前にユーザーに確認します。

# 書く場所ごとの役割

- コードには How（どう実現するか）を書きます。
- テストコードには What（何を満たすべきか）を書きます。
- コミットログには Why（なぜその変更をしたか）を書きます。
- コードコメントには Why not（なぜ別の方法を選ばなかったか）を書きます。

# 文章の書き方：パラグラフライティング

ユーザーへの回答、作業報告、設計ドキュメント、PR の説明文など、日本語で説明的な文章を書くときは、パラグラフライティングで書きます。

## 段落の構成

- 一つの段落には一つのトピックだけを置きます。話題が変わったら段落を分けます。
- 段落の最初の文（トピックセンテンス）で、その段落の主張を言い切ります。後続の文は、その主張の根拠、具体例、説明に限ります。
- 段落の先頭の文だけを拾い読みしても、文章全体の論旨が追えるように書きます。
- 段落の先頭では、前の段落との論理関係を接続表現（「しかし」「実際」「そのため」「であれば」など）で示します。

## 論証の進め方

- 結論を先に書きます。背景や経緯から書き始めて最後に結論を出す構成にはしません。
- 論証は一方向に進めます。懸念や反論の処理を終えてから結論を述べ、同じ結論を言い直しません。
- 因果を述べるときは、なぜそうなるのかを一文で示します。「A だと B になる」とだけ書いて理由を省略しません。

## 作業報告への適用

- 作業完了の報告では、最初の段落で結果（何を変更し、どうなったか）を述べます。
- 変更の理由や判断の根拠は、結果の段落の後に置きます。
- 未解決の問題やユーザーに確認してほしい点は独立した段落にし、その段落の最初の文でそれとわかるようにします。

## 書式

- 一文ごとに改行し、段落の区切りは空行で示します。
- 箇条書きは、手順、選択肢、項目の列挙など、本当に並列な情報に限って使います。論証を箇条書きで代用しません。

## 適用しない場面

- 一文で済む回答や、確認への短い応答は、段落構成を意識せずそのまま答えます。
- コードとコードコメントは、プロジェクト既存の規約に従います。

## 例

悪い例（結論が最後まで出てこない）：

```
現在、セッション情報はアプリケーションサーバーのメモリに保持しています。
スケールアウト時にユーザーがログアウトされる障害が発生しています。
そこで、セッションストアを Redis に移すことを提案します。
```

良い例（最初の文で主張を言い切る）：

```
セッションストアを、アプリケーションサーバーのメモリから Redis へ移すことを提案します。
現状ではセッションが各サーバーのメモリにあるため、スケールアウトで振り分け先が変わるとユーザーがログアウトされます。
```
